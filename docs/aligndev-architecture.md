# aligndev Architecture

`aligndev` is the CLI an assistant uses: it prints the playbook (`guide`), delegates work to a coding agent (`code`), inventories the host's projects (`project`), and uses AlignFirst's unified workspace lifecycle. Its users are agents, so its `--help` and guides are the user reference. This document covers what they leave out. The [README](../packages/aligndev/README.md) covers setup and configuration.

## Source Structure

| Path | Responsibility |
| --- | --- |
| `src/cli.ts` | Entry point: dispatches commands and loads settings; creates command-scoped model discovery. |
| `src/assistant-harness.ts` | The assistant's harness, resolved at each invocation, and the guide platform derived from it. |
| `src/config.ts` | `~/.alignfirst/aligndev.settings.json`: tolerant settings, reference validation, effective selection and child environment. |
| `src/code/` | `aligndev code`: arguments, prompt, run, session file, adapters, models, quota. |
| `src/code/harness-environment.ts` | Each coding agent's markers, session variables and native directory variable, read by detection and by the child environment. |
| `src/memory/` | The AlignDev memory: the SQLite adapter and the `store` table. |
| `src/guide/` | `aligndev guide [--channel <surface>]`: topics by context and the template renderer. |
| `src/guide/global-instructions.ts` | The dispatcher's global section, built from `~/.alignfirst/ASSISTANTS.md`. |
| `src/project/` | `aligndev project`: discovery, status, port claims and free-port lookup; AlignFirst report parsing and work-files gate calls. |
| `@alignfirst/workspace/git` | Shared Git inventory/path helpers; lifecycle commands belong to AlignFirst. |
| `templates/guide/` | The dispatcher, the playbook and the guides, rendered per platform and surface. |

Templates use `{{ALIGNDEV}}`, `{{ALIGNFIRST}}` placeholders for rendered command forms. `src/command-form.ts` resolves invocation once through `@alignfirst/docmap/invocation`, separating launcher (`direct`, `packageRunner`, `projectScript`) from actual runtime (`node`, `bun`). Explicit runner evidence wins over lockfiles; a project script requires manifest, entry-point and immediate-parent agreement. User-agent metadata alone does not prove either a script or a runtime.

Under npm/npx, counterpart commands use `npx -y alignfirst`; under Bun runtime they use `bunx --bun alignfirst`. Verified scripts are retained only for self follow-ups. Direct Bun entry launches also produce explicit Bun package-runner commands. Published bins keep Node shebangs, so ordinary `bunx` uses Node when it is installed, and Bun itself otherwise. No automatic runtime re-execution occurs.

`src/alignfirst-cli.ts` spawns the structured executable and fixed argv plus operation arguments, never split rendered text. This covers config reports, plans checks, ticket open/reservation/catchup, companion context and diagnostic `--version` probes. Missing/outdated-report diagnostics describe the selected runner, explicit Bun runtime when applicable, and direct executable resolution. Delegated prompts use the same counterpart selection; the native coding agent keeps its own executable policy and prerequisites.

A render has a platform and a surface under `openclaw` (`--channel slack|discord|app`). The platform derives from the assistant's harness: `openclaw` for the `openclaw` harness, `codingAgent` otherwise. Under `codingAgent`, the render also carries the assistant's harness, absent when unrecognized. Without a topic, `aligndev guide` prints the dispatcher, the only `openclaw` render without a surface. `code` without `--channel` renders the `app` surface, for operators who validate profiles outside any session. `--channel` alone prints the surface's playbook. The entry topics, `working-session` and `channel-handling`, print the playbook first. The topics are keyed by context: `thread` (Slack and Discord), `app`, `codingAgent`. `{{GUIDE}}` renders as `aligndev guide --channel <surface>` or `aligndev guide`, so every later guide call keeps the surface.

The dispatcher ends with a global section, built from `<home>/.alignfirst/ASSISTANTS.md`, where `<home>` is the home that `loadConfig` uses. The path is fixed. No other render carries the section, `guide code` and the entry topics included:

| Platform | File has content | File is absent or blank |
| --- | --- | --- |
| `codingAgent` | Section with the block | Section without the block |
| `openclaw` | Section with the block, naming the operator as the only writer | No section |

The block is `<assistant-instructions scope="global" file="…">`, with the file's absolute path. The content is inserted verbatim, trailing whitespace trimmed, outside block and placeholder rendering: a `{{ALIGNDEV}}` written by the user stays literal. A file holding only whitespace counts as blank. A read error other than a missing file fails `aligndev guide` with `Cannot read <path>: <reason>` and exit code 1.

`resolveAssistantHarness` reads the caller environment at each invocation, in this order:

1. `ALIGNDEV_ASSISTANT_HARNESS`: `openclaw`, `claude`, `codex`, `pi` or `agy`. Any other nonempty value fails.
2. The single detected coding agent. Several detected agents leave the harness unrecognized.
3. `OPENCLAW_SHELL=exec`: `openclaw`.
4. Otherwise, the harness is unrecognized.

Detection precedes `OPENCLAW_SHELL` because an agent that `aligndev code` launches from OpenClaw inherits that variable, which OpenClaw's own CLI relies on. The agent environment keeps `OPENCLAW_SHELL` and drops `ALIGNDEV_ASSISTANT_HARNESS`, so an explicit harness applies to one invocation. An operator shell outside OpenClaw sets the variable to render the OpenClaw guides.

Variants sit in blocks, each marker alone on its line. A block names a fact, and a line is kept when every block around it holds:

- A platform block, `{{#openclaw}}` or `{{#codingAgent}}`, sits at the top level.
- A surface block, `{{#slack}}`, `{{#discord}}` or `{{#app}}`, and `{{#thread}}` never sit inside a `{{#codingAgent}}` block.
- A harness block, `{{#claude}}`, `{{#codex}}`, `{{#pi}}` or `{{#agy}}`, sits inside a `{{#codingAgent}}` block, never inside another harness block. It holds for the assistant's harness; every harness block holds when the harness is unrecognized.
- `{{#conversation}}` sits anywhere.

`thread` and `conversation` are derived: `thread` holds on Slack and Discord, `conversation` on `app` and under `codingAgent`.

Playbook-topic rendering reads no project report and performs no guide-file discovery. Every platform asks the assistant to run `alignfirst assistant-instructions` in the selected workplace. AlignFirst prints project guidance, then the project's assistant guide in an `<assistant-instructions scope="project">` block carrying its absolute path. The guide is the optional `ASSISTANTS.md`; a missing or blank guide leaves the guidance alone. Editing uses `locations.assistantInstructionsFile` from `alignfirst config --json` in that worktree; it always names the file to read, edit or create. Assistant instructions and coding-agent context remain distinct. The `code` topic still reads the report in the actual cwd for independent project profile selection.

## Running the Agent

`aligndev code` runs the agent as a direct **foreground** child until it exits. It writes the transcript to a durable per-run file and, unless `--quiet` is given, streams it to stdout. Quiet mode keeps the initial `Session file:` line, new child `Session ID:` and failure diagnostics. The CLI never backgrounds or detaches itself.

- Under OpenClaw, the assistant runs it through `exec` with `background: true` and `timeoutSeconds: 0`, and chains `openclaw system event --mode now --session-key <key>` onto the command.
- A Claude Code assistant launches with `run_in_background` and an explicit `timeout` set to the maximum stated by its Bash tool. Claude Code wakes the assistant on exit.
- A Codex assistant retains its established background facility; where no completion bridge is configured, they use the next-user-turn status fallback. Claude Code/Codex retain their sandbox elevation.
- An Antigravity assistant runs every AlignDev and AlignFirst command outside its sandbox (`BypassSandbox: true`) and launches through `run_command` as a background task (`IsDaemon: false`). Antigravity wakes it with a system message when the command exits. Pi work does not certify or replace these integrations.
- A persistent Pi assistant uses the generic `background` tool to launch an ordinary quoted CLI command with `--quiet` and a unique per-run `--meta`. The guide owns those flags, not the extension. A notice triggers a handle-ownership check, then exact-file or unique-key `status --result` retrieval from the original worktree. The assistant's harness and the agent's harness are independent. See [Pi Extensions](pi-extensions.md) for package and native delivery boundaries.

The prompt reaches the agent through stdin. An adapter may wrap it (`formatInput`), as `agy` does with one `user` event line. A new session's prompt opens with a run context. It tells the agent that ending its turn kills its subagents and background commands, so it must wait for them first. The effective profile starts with a copy of the caller environment and removes what a package launcher injected: `NODE` when it equals `npm_node_execpath`, verified forced-Bun shim directories from PATH with their matching runtime metadata, every lowercase `npm_*` variable, `INIT_CWD`, and the leading run of PATH entries that end in `node_modules/.bin` or `node-gyp-bin`. Uppercase variables such as `NPM_TOKEN` stay. It then removes its `unset`, then applies literal `env` values and the directory selection (set a resolved string or remove the native variable for null), strips every harness's session identity, then applies adapter-required values. `buildAgentEnv` owns this order; Claude's background-wait ceiling always wins. Ordinary Bun installations and explicit profile PATH overrides remain intact. This external-process baseline also applies to explicit quota sources; owned AlignFirst calls retain the original caller environment and explicit Bun runner. The finalized `CodeConfig.childEnv` reaches model discovery, adapter state, spawn and Codex rollout lookup. Caller environments are immutable; run metadata contains no environment snapshot.

`HARNESS_ENVIRONMENTS` (`src/code/harness-environment.ts`) lists each coding agent's markers and the session variables it gives the commands it runs. Stripping removes every name of every harness, whatever the value, and `ALIGNDEV_ASSISTANT_HARNESS`. Harness session variables go because the child starts its own session of its harness, with its own identity. `AI_AGENT` therefore always goes: it names the agent that runs the command. The Claude Code row is a bounded set, so user settings such as `CLAUDE_CODE_USE_BEDROCK` stay. Some variables pass through on purpose:

- `TRACEPARENT` and `TRACESTATE` nest the child's trace under the assistant's tool call that launched it.
- Host-app identity variables, such as Paseo's `PASEO_AGENT_ID`, `PASEO_WORKSPACE_ID` and `PASEO_AGENT_CWD`, stay because the child gets no identity in the host app: it acts there as the assistant's hands. Under Paseo, `paseo run` from the child runs in the assistant's workspace, `paseo send` is signed as the assistant, and `schedule --target self` reaches the assistant, which outlives the child.
- `OPENCLAW_SHELL` stays, as described above.

A profile's `unset` removes any of them.

### Session File

The session file is the durable handoff of a run. Its frontmatter holds `profile` (named selection or null), `agent`, the user-facing `model`, the `effort` (null for the native default; an absent key reads as null), `sessionId`, `status` (`running`, then `succeeded` or `failed`) and an optional `exitReason`; a `---- Result ----` block closes it. The block lists every completed response oldest first, separated by `---- Later result ----`. Each non-empty Claude `result`, each Pi assistant message ending with `stop` and Antigravity's successful `result` count as a response. Earlier responses also precede failure or termination text. The completion turn finds it with `aligndev code status`. A response containing `---- Result ----` on its own line can be truncated by status because the legacy format also uses that line as its boundary. Fixing this ambiguity requires unambiguous payload framing with legacy-file support; it remains a follow-up limitation. String metadata containing control characters is JSON-quoted on one physical line, preserving embedded newlines in exact profile/model names through completion and resume.

Each new record carries `machineId`, a random UUID read from `~/.alignfirst/machine-id`, created on first use by writing a temporary file and hard-linking it into place. Concurrent creators read the winning id. An empty or unreadable file is an error; older records read as `machineId: null`.

Session files live under the project's `_aligndev` location, read from `alignfirst config --json`: `<ticket>/_aligndev/`, or `_aligndev/` without a ticket. That location is below the project's `.plans/`, unless a companion directory holds a separate tree.

A run is written as `<stamp>.running.md` and renamed to `<stamp>.md` when it ends, by completion or by sealing. `alignfirst sync` leaves `_aligndev/*.running.md` out of its snapshots, so a log reaches the work-files repository only once its run has ended. `code status <path>` resolves a retained `.running.md` path to the completed file. Records written before this convention keep their name and their `running` status until their run ends.

The CLI creates a missing companion before launch, independently of permission mode. Claude Code, Codex and Antigravity normal modes add it through `--add-dir`; Pi uses ordinary OS access. When some AlignFirst files live there, a new session's prompt starts with `alignfirst context`. See [Companion Directories](companion-directories.md).

`status` accepts exactly one file, `--ticket`, `--no-ticket`, or `--meta` selector. Scope/key selectors choose the newest matching active run, so asynchronous callers use a unique key per run and retain the resolved exact path. `status --result` adds the terminal Result block when present, without transcript output; running runs show metadata only. It has no numeric final-text cap. `readCompletion` currently reads the whole file into memory. A successful status query exits `0` even when the run failed; launch/run exits are `0` for success, `1` for ordinary failure and `2` for authentication.

### Termination and Status

On handled termination, the CLI seals the session file (`status: failed`, `exitReason: terminated`), sends `SIGTERM` to its child, and escalates to `SIGKILL` after its two-second grace. The assistant's harness owns attached process-tree supervision; this does not promise crash-proof descendant cleanup.

Abrupt host loss, a crash or `SIGKILL` can leave a stale `running` status. Status queries and launch scans seal a record as `terminated` only when its `machineId` matches this installation and its process is conclusively gone: probing the pid returns `ESRCH`, or the pid exists and its readable Linux start time differs from the recorded one. Status prints `machineId` after `pid`.

Foreign and legacy records stay untouched, as do records with no pid or an inconclusive process probe (`EPERM`, or a live pid with no recorded or readable current start time). Running records still block applicable launches. Guard errors name their path; foreign and legacy records must be checked on their machine, or have their `status` set by hand once the run has ended.

The `contextTokens` line reports what the run left in the agent's context window; a resumed session keeps growing. For Antigravity, it sums `input_tokens`, `cache_read_tokens` and `output_tokens` of the latest completed `agent_response` step, since `result.usage` is cumulative over the conversation.

### Authentication

When the agent's login on the host is missing or expired, `aligndev code` detects the failure in the agent's stream, seals the session file with `exitReason: auth_required`, and exits `2`. `renderAuthenticationFailure` (`src/code/login.ts`) writes one text as the Result block and as the stderr diagnostic: an OpenClaw assistant reads the session file only. The agent's own error follows it in the Result block, under a label line: provider output may hold a credential, so it stays out of the diagnostic. The guide tells the assistant to relay the text without that error, and to retry only once the agent is authenticated.

The text names the profile and gives its login command: `cd` to the run's directory, then the native CLI under `env`, followed by the harness's own step, such as `/login` for Claude Code. `env` reproduces what selects the account:

- the profile's `unset` and the names of its `env`;
- the native directory variable as the agent ran with it, set or removed: another shell may hold a different one.

Three values are printed, all directory paths: a `configDir` string, the native directory variable inherited from the assistant's session, and the inherited HOME, which identifies the agent's OS user. A profile `env` value is never printed, whatever its name: its place holds a `${OMITTED:?…}` expansion, which the shell refuses until the value from the settings file replaces it. The rest of the inherited environment is never listed. These paths reach the work-files repository with the session file. The command targets bash or zsh. Values are shell-quoted; a control character is written as its UTF-8 bytes in ANSI-C quoting, which decodes under any locale.

Help prints the same command through `renderLoginInstructions`, for the directory it runs from. `describeNativeStorage` gives help and the other failures their storage-origin labels, with no environment value: string `configDir`, explicit unset by `configDir: null` with native defaults, profile environment override, inherited variable or profile removal, including HOME/USERPROFILE context.

### Tickets

A new protocol session needs a ticket. `--no-ticket` reserves the next side ticket through `alignfirst ticket --side`. `--catchup` loads the ticket's history through `alignfirst ticket --catchup` before the protocol and message. A protocol run is refused while another protocol run is active in the same worktree or on the same ticket, since `alignfirst ticket --next` reserves no work-file prefix. Runs without a protocol neither block nor are blocked.

## Coding Agents

Four adapters (`claude-agent.ts`, `codex-agent.ts`, `pi-agent.ts`, `agy-agent.ts`) build CLI arguments, parse streams and recognize authentication failures. Antigravity runs one turn per process in its stream form (`--input-format stream-json --output-format stream-json`) and resumes from any directory. Pi targets 1.4.0's JSON/print settlement contract, preserves its native conversation for resume, and requires that resume use the recorded directory. The synchronous subagent package is optional in that child environment; it is not an adapter dependency.

- **Permissions:** normal runs use Claude's `--permission-mode auto`, Codex's `--sandbox workspace-write` or Antigravity's auto mode, which no flag selects. The profile's `skipPermissions` selects their bypass flags. Antigravity's sandbox hides the main checkout of a linked worktree, and with it the repository that `git` needs. A normal Antigravity run from a linked worktree therefore adds the git common directory through `--add-dir`, when `git rev-parse --git-common-dir` differs from `--git-dir`. Antigravity starts its shell in the workspace directory that sorts first by path, which an added directory can be: with any `--add-dir`, the adapter opens the prompt with the working directory to run commands in. Pi uses ordinary OS permissions and saved project trust, without forced approval; that setting has no effect on Pi.
- **Models:** A selector that holds `{latest}` is a pattern. The placeholder stands for a version: a major number, optionally followed by `.` or `-` and a minor number, each of one to three digits. The executable resolver matches a pattern against the whole text of each selector of the harness catalog and returns the selector with the newest version. It fails when several selectors share that version. The catalog comes from the remembered model list while it is fresh; see [Model Lists](#model-lists). A selector without `{latest}` passes unchanged, without a catalog call. So does every Claude selector: settings validation keeps `{latest}` out of `claude` profiles. The catalog selectors are Codex's slugs through `codex debug models --bundled`, Pi's `provider/id` through the `get_available_models` command of `pi --mode rpc --no-session`, and Antigravity's ids through `agy models`. A pattern matches an Antigravity id with or without its effort ending, and both select the id without it. Pi's RPC stdout carries only protocol records, so extension output cannot alter the catalog. AlignDev closes Pi's stdin after the LF-terminated response. Pi reads stdin only after its extensions' startup handlers, so an extension dialog before the response cannot be answered. Unless the dialog's own timeout expires before the deadline, AlignDev stops Pi at once and reports a fixed error that suggests pinning the model. Dialogs after the response are ignored. Every catalog command has a 30-second deadline and an 8 MiB output limit in bytes. On failure, AlignDev stops buffering, closes stdin, sends `SIGTERM`, then `SIGKILL` after 5 seconds, and reports the failure once the process has exited. It then closes the output pipes, which a descendant can still hold. A catalog that reports a missing sign-in, Pi's empty model list or Antigravity's sign-in error, ends the launch with `auth_required` and the login instructions, without the catalog's output. Each profile has built-in aliases, from the biggest model to the smallest. Claude's `fable`, `opus`, `sonnet`, `haiku` pass unchanged. Codex's `astra`, `sol`, `terra`, `luna` map to `gpt-{latest}-<alias>`, and Antigravity's `carbon`, `neon`, `hydrogen`, `flash` to `gemini-{latest}-<alias>`. A Pi profile has the aliases of its `modelFamilies`, which maps a family (`gpt`, `claude` or `gemini`) to the text placed before the family's pattern: a Pi provider, with an optional gateway prefix. A nonempty profile `models` replaces the accepted names. Otherwise a profile accepts its built-in aliases plus its `modelAliases` names, in that order. The `code` guide shows the list as biggest first. A Pi profile that declares nothing accepts no model and runs Pi's own default. A chosen name is validated against the accepted names, expanded once through `modelAliases` (`expandModelAlias`), replaced with its pattern when the result is a built-in alias (`expandBuiltInAlias`), then passed to the executable resolver. Without `--model`, new sessions use profile `defaultModel`, else the child's default; resumes retain and validate the latest recorded model, ignoring new-session defaults. A disallowed retained name requires `--model`; null retains the native conversation default. Current alias mappings apply to retained names. The file records the chosen name, or `null` for the child's default.
- **Effort:** `resolveEfforts(harness, efforts)` in `efforts.ts` returns a profile's accepted levels: its nonempty `efforts`, else the built-in levels of its harness. The adapters pass the level unchanged: Claude `--effort <level>`, Codex `-c model_reasoning_effort="<level>"` (a TOML string, before `resume`), Pi `--thinking <level>` (it overrides a thinking suffix of `--model`), Antigravity `--effort <level>`. Selection follows the model: `--effort`, else for a new session the profile's `defaultEffort`, else none. A resume retains and validates the latest recorded effort; a level the profile no longer accepts requires `--effort`, and null stays null. Claude and Codex apply the level to one invocation, so every run passes the effective effort. No level is checked against the model.
- **Background work:** after the agent's turn, `claude -p` waits for its background subagents and commands, then wakes it for another turn. By default, it kills that work after 10 minutes of idle waiting; Claude runs set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` to wait until it ends. Each turn closes with its own `result` event, and the session file keeps every completed response. Antigravity also waits for a non-daemon background command and wakes the agent, but closes the run with a single `result`.
- **Resume:** the report and latest relevant session record are read before profile resolution. The same latest record supplies profile, native agent, model, effort, ticket and cwd decisions. Same-agent and active-run guards precede ticket/session-directory side effects and catalog subprocesses. Claude, Codex and Antigravity track expected native IDs from `RunConfig.resume`; a missing or changed identity fails permanently. The runner then stops the child at once, for every adapter: `SIGTERM`, then `SIGKILL` after the termination grace. For Antigravity, an unknown `--conversation` starts a new conversation, whose different ID arrives at `init`, before the model is called: the prompt never executes. Pi retains its version-3 header and real-cwd guards. No account fallback or replacement conversation is accepted. Agentless legacy sessions remain readable but need a new session.
- **Selection:** `resolveCodeConfig(config, env, { project, explicit, recorded })` returns the effective `profile`, harness, normalized launch settings, retained typed quota settings and finalized `childEnv`. It resolves the assistant's harness, validates the references, then selects for new sessions, help, `guide code` and quota: `--profile` → project registry selection → on resume, the latest recorded named profile → the assistant's profile. The assistant's profile applies its `defaultAgentProfile`, followed once, or itself. Without an assistant's profile, a Claude Code, Codex, Pi or Antigravity harness uses its built-in defaults, and an `openclaw` or unrecognized harness uses `code.fallbackProfile`. Without that key, the error names the remedies; with one enabled coding-agent profile, it prints the line to add. A named reference never falls through: a missing, disabled or `openclaw` target fails and names its origin. No inheritance or profile merging occurs. A per-agent flag never chooses the harness.
- **The assistant's profile:** under `openclaw`, the enabled `openclaw` profile. It describes an assistant and launches nothing: it accepts `harness`, a required `defaultAgentProfile` and `disabled`. Under a coding agent, the enabled profiles of that harness whose `configDir` is compatible with the session's native directory variable, read from the caller environment: null an unset variable, a path the same directory after normalization. A variable set to the native default path does not match null. Profiles with an omitted `configDir` match anything and are candidates only without such an exact match. Among several candidates, the one flagged `default: true` wins; without a flag, the launch fails and lists them.
- **Detection:** `HARNESS_ENVIRONMENTS` is the single source of markers and session variables. Claude uses `CLAUDECODE=1`, Codex `CODEX_THREAD_ID`, Pi `PI_CODING_AGENT=true` or `AI_AGENT=pi`, Antigravity `ANTIGRAVITY_AGENT=1`. Both Pi markers count as one harness. Several detected harnesses leave the assistant's harness unrecognized, so only a named profile applies, `code.fallbackProfile` included. Native directory variables map through `CONFIG_DIRECTORY_VARIABLES` in `src/code/harness-environment.ts`; `agy` has none. Environment/path validation rejects NUL, invalid names, overlapping env/unset and config-directory conflicts.
- **Directory selection:** coding profiles and enabled quota sources accept `configDir?: string | null`. Omitted/undefined inherits the caller's native variable unless `env` or `unset` changes it; otherwise native defaults apply. Strings normalize against the settings directory and supplied home, then set `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `PI_CODING_AGENT_DIR`. An `agy` profile or quota source rejects `configDir`: Antigravity keeps one store under `~/.gemini` and one account per OS user. Every enabled `agy` profile therefore describes an Antigravity session, through the omitted-`configDir` path. Null remains explicit in loaded/resolved settings and removes only the corresponding variable through the shared environment-construction helper. Both null and strings conflict with that variable in `env`/`unset`. Caller environments and stored `unset` arrays remain unchanged; other path fields stay string-only.
- **Settings boundaries:** `loadConfig` validates structure. Every resolution checks the references of enabled profiles (`defaultAgentProfile` and `code.fallbackProfile`), at most one `default: true` per harness and one `openclaw` profile among enabled profiles, and the selected model defaults. `loadConfig` also checks each coding profile's `defaultEffort` against its accepted levels, disabled profiles included. These checks fail even with a valid named selection; false and omitted defaults are equivalent. A disabled profile is absent for selection; its shape is still validated. Status reads durable records without loading settings, so malformed or retired settings and dangling profile references never block it. Commands that load settings validate recognized values. A profile without `harness` fails, unless it carries `agent`. Unknown keys at the root, `code`, each profile and each quota object are ignored with `console.warn` on stderr. Profile, environment and alias dictionaries remain dynamic maps. Warnings include escaped property paths with dynamic map names redacted, never values. Retired keys warn with a migration hint and supply no legacy semantics: `platform`, `code.profile`, a profile's `agent` beside `harness`, direct launch fields and `code.defaultProfiles`. One exception: `mapLegacyAgent` reads a profile's `agent` without `harness` as `harness`, in memory, with a deprecation warning. It is not a general deprecated-alias rule. The settings file is never rewritten. Historical blank or missing profiles read as null and are not rewritten merely to add a field.
- **Discovery isolation:** `main()` creates one memory, one executable resolver and one `ModelLists` per invocation, and closes the memory at the end. Within the process, catalog caching is scoped by effective environment identity and harness, so repeated programmatic invocations cannot reuse a different profile's installation/PATH. Catalog and injected executable-resolver failures produce fixed diagnostics without native stderr or arbitrary error text, including in the durable completion result. Codex occupancy still requires rollout cumulative totals to match stream totals; lookup uses the selected native environment rather than ambient `CODEX_HOME`. If that environment supplies neither `CODEX_HOME`, `HOME` nor `USERPROFILE`, context is reported unavailable instead of searching the caller's native store.
- **Quota boundary:** `resolveQuotaConfig(code, callerEnv)` returns disabled `source: "none"` or a native `claude`, `codex` or `agy` source with a finalized environment. Omitted native quota uses `childEnv`; Pi needs an explicit source. An explicit source starts from the original caller environment and applies only quota overrides, its own omitted/null/string directory selection and identity stripping. Coding and explicit-quota resets are isolated; omitted native quota inherits the finalized coding reset. Disabled quota accepts no other recognized fields, including `configDir: null`. It never copies Pi credentials or infers an account from a model. `QuotaReader(source, { cwd, env })` executes only native protocols; CLI presentation handles profile/source labels and disabled/unsupported diagnostics. Reports belong to that CLI's account, without verified pairing to the coding account.

Ordinary developer guidance omits `configDir`; null is a deliberate native-default reset and custom strings remain valid. A string naming the default path still sets the variable. On macOS, setting Claude's default path can select different Keychain credentials from leaving `CLAUDE_CONFIG_DIR` unset. No path comparison, credential copying or account fallback is used. Confirm the intended mode before changing existing selections; a reset leaves HOME, PATH and API-key precedence intact.

OpenClaw deployment inventory instead requires null or a string for every enabled coding profile and enabled explicit quota source. It rejects an `agy` profile or quota source; see [issue #163](https://github.com/paleo/alignfirst/issues/163). It also requires one enabled `openclaw` profile whose `defaultAgentProfile` names a provisioned coding profile. Null resolves to the service home's native default path for filesystem inventory, whose `configDir` output remains an absolute string. Native invocations read selection mode from the named profile/quota settings and unset the variable for null or set the resolved value for a string. Filesystem deduplication cannot collapse these invocation modes. Upgrade the CLI, inventory/policy helpers, settings and runbooks together through controlled maintenance; existing strings are not converted automatically.

### Native Quota Processes

Claude uses the native `/usage` print command and extracts limits before local insights. Its privacy translation operates on a copy of the effective environment. Antigravity runs `agy -p /usage --output-format json` and reports each bucket of `command.data.groups` as `1 - remaining_fraction` used. Codex initializes `app-server`, sends `initialized`, then reads `account/rateLimits/read`. A present `rateLimitsByLimitId.codex` is authoritative; malformed named data cannot fall back to legacy `rateLimits`. Legacy identity must be absent, null or `codex`. Valid windows survive independently, with finite percentages in 0–100, positive finite durations and valid nonnegative reset timestamps. Duration determines labels regardless of primary/secondary order.

All three protocols retain the injectable `QuotaProcessAdapter`. The default process runner caps combined stdout/stderr at 1 MiB and the request at 30 seconds. Completion closes stdin, sends TERM and awaits direct-child/pipe closure. After 250 ms it sends KILL, with a further one-second cleanup bound. Failure to discharge ownership is explicit; exit guards remain until ownership ends. Error output is never echoed into diagnostics. This supervises the attached native child, without importing Pi process-tree packages or promising descendant/crash recovery.

### Historical Profile Selection

`ProfileSelection.recorded` preserves three states. Undefined permits automatic selection. A string takes precedence over the assistant's profile and the fallback, so changed defaults cannot redirect a named resume. `--profile` or the project registry selection may replace a deleted recorded name; automatic selection cannot rescue it.

Null protects historical unnamed conversations. Only `--profile` or the project registry selection replaces it. Otherwise the resolver constructs the built-ins of the assistant's harness, ignoring configured profiles and flags; an `openclaw` or unrecognized harness fails. The new record keeps null, and the original transcript stays byte-identical. The recorded agent does not replace harness resolution; existing same-agent and native-identity guards still apply.

## The AlignDev Memory

The memory is `<home>/.alignfirst/aligndev.store.sqlite`, where `<home>` is the home that `loadConfig` uses. The AlignDev instances of the OS account share it. It holds paths and native CLI versions, so it stays local to the machine. Its only content is the model lists.

- **Adapter:** `src/memory/sqlite.ts` is the only module that knows the runtimes. It loads `node:sqlite` (`DatabaseSync`) under Node and `bun:sqlite` (`Database`) under Bun, chosen by `process.versions.bun`, each through a dynamic import. `bun-sqlite.d.ts` declares the Bun surface; no Bun type reaches an exported signature. Under Node 22, the adapter drops the SQLite `ExperimentalWarning` during the import and the first open; other warnings still print. Node has `node:sqlite` without a flag from 22.13, hence the package's `engines`.
- **Connection:** `createMemory` opens the file at the first call, so a command that never reads it creates nothing. Each connection sets `PRAGMA busy_timeout = 5000` and keeps the default journal mode. Every write runs in a `BEGIN IMMEDIATE` transaction. No transaction stays open while a native command runs.
- **Schema:** one ordinary table, `store`, keyed by `realm` and `entry`. A `STRICT` table would reject the type name `TIMESTAMP`. No table or column name is an SQL keyword, reserved or not. `realm` is `global` for a row of the OS account; a later project row takes `project:{project-path}`. `entry` is written as a Redis key: `type:id` pairs, then the attribute. `entryName` escapes `%` and `:` of an id as `%25` and `%3A`. `payload` is JSON whose shape belongs to the attribute. `updated_at` is SQLite's `CURRENT_TIMESTAMP` text, in UTC. A row whose payload or time cannot be parsed reads as absent.
- **Migrations:** `PRAGMA user_version` holds the schema version. Each step runs in its own `BEGIN IMMEDIATE` transaction that reads the version again, so two instances cannot apply it twice. A migration may delete the rows of a rebuildable attribute, such as the model lists with `entry GLOB 'harness:*:models'`.
- **Unavailability:** when opening, migrating, reading or writing fails, or when `user_version` exceeds the known steps, the memory keeps the reason and stays unavailable for the invocation. Reads find nothing, writes do nothing, and the file stays untouched. Only `aligndev code models` reports it.

### Model Lists

`src/code/model-lists.ts` owns the attribute `models`: one row per harness and profile, under `harness:{harness}:profile:{profile}:models`, or `harness:{harness}:models` for the built-in profile. The payload holds `cliVersion`, the first line of `<cli> --version` or an empty text on failure; `configDir`, the native directory variable of the agent's environment or null, always null for `agy`; and `models`, the native ids as the catalog lists them. Antigravity ids keep their effort ending; the split applies at read time. A launch and `aligndev code models` build their discovery context with `modelDiscoveryContext`, so both address the same row.

A list is fresh when its `cliVersion` and `configDir` match and its `updated_at` falls on the current local day. A `{latest}` launch reads the version, then resolves from a fresh list. Otherwise the catalog command runs and its list replaces the row. A fresh list that cannot resolve the pattern triggers one catalog command before failing. When the catalog command fails, a stored list of the same directory resolves the pattern and the row stays unchanged. Without such a list, the failure is reported as without a memory. An unavailable memory runs the catalog command at each launch, without the version command.

`aligndev code models [--profile <name>] [--refresh]` (`src/code/models-cli.ts`) covers the enabled coding-agent profiles, or the effective built-in profile without any. It reads no project report, and its report runs no native command. `--refresh` runs the version and catalog commands of each profile with a pattern, outside the process cache, and shows a changed model with both values. A failing profile keeps its row and writes the launch diagnostic of `describeModelFailure` (`src/code/model-failure.ts`) to stderr; the command then exits 1. With an unavailable memory, `--refresh` exits 1 without any native command.

## Unified workspaces

`alignfirst workspace` owns creation, adoption, preparation, inventory and cleanup. AlignDev has no second lifecycle engine or command aliases. The assistant runs standard preparation directly, in the foreground, and keeps coding delegation separate. It uses the same commands for configured and manifest-free projects. The latter are protocol-ready, with no dependency installation, build, port allocation or service startup.

The host validates effective work files and selected runtime storage before creation. Project runtime requires ignored, untracked `.local-wt/`; companion runtime creates no checkout runtime directory or link. Linked worktrees share main's effective project-local plans and usable untracked `.local`; companion plans resolve directly. Tracked `.local` stays branch-local. Failures retain branch/files/identity and print a precise retry command. See [Workspace Architecture](workspace-architecture.md) for runtime state and target-owned cleanup.

`src/project/plans.ts` runs `alignfirst plans check --json` and returns `plans.target`. AlignFirst refuses project-tracked effective plans through both logical and resolved paths. From a linked worktree, it requires the same real target and `in` as the main worktree. Separate work-files repositories remain supported; an unused tracked project copy does not block companion plans. New/resumed coding launches apply this gate before stale-session reconciliation, ticket/session writes or model discovery. Historical status, help and inventory remain readable. The playbook's work-files runbook calls `alignfirst plans check`.

The `work-files-setup` topic is the sole separately authorized companion preparation recipe, before ticket reservation, request capture or coding effects. Workspace setup never provisions missing plans or changes companion selection. A shared link grants no sandbox access; native coding-agent permissions remain unchanged.

External tools adopt through `alignfirst workspace setup` and run `teardown` before their own deletion. `remove` adds protected Git deletion while retaining branches; stop/purge failures retain retry state. Consultation and no-branch status exceptions create no worktree. Existing installations follow [the clean-break upgrade runbook](upgrading-multi-stack-workspaces.md).

## Project Inventory

The scan starts at `--root`, then `projectsRoot` from the settings, then the working directory. Any directory is a valid root. For each child directory:

- A Git main worktree is a project. The scan does not descend into it.
- A linked worktree is a workspace of its project.
- Any other directory is a group, scanned in turn.

`--max-depth <n>`, a positive integer with a default of 5, applies to `list`, `status`, `doctor`, `ports` and `free-ports`. The root's children are at depth 1. Hidden directories and `node_modules` are skipped silently. The root itself must be readable; a missing or unreadable root fails the scan.

After the walk, one `alignfirst config --json <dir>...` call, run from the root, reads the reports of every main-worktree candidate; entries match candidates by position. A failed call, or an output without a `reports` array of the expected length, fails the scan with the AlignFirst upgrade diagnostic. An entry with `error` becomes an issue, and its path joins `unreadableProjects`: that project's range is unknown.

`skippedDirectories` lists what the scan left out, with a reason: `outsideWorktree` (a linked worktree whose main worktree is outside the scan), `workFilesRepository` (a repository holding another project's `.plans`), `symlink` (not followed), `unreadable` and `maxDepth` (a group at the depth limit). These entries are informative and never fail `doctor`.

- These are inventory issues: a group with a root `alignfirst.json` or `alignfirst.jsonc` (the group is still scanned), two projects sharing one companion directory, unreadable projects and overlapping project ranges. `aligndev project doctor` succeeds only without any issue.
- `list` and `status` carry the registry's independent `aligndev: { profile } | null` selection alongside companion and location data. Inventory reports it without resolving a launch profile or requiring an available coding agent. A missing top-level `aligndev` field in `alignfirst config --json` is an outdated contract and requires an AlignFirst upgrade.
- A project's sole range declaration is `devServer.ports` in its selected merged configuration, including companion-selected recipes.

### Port Claims

Only a main worktree's range counts; a range declared in a linked worktree counts once it reaches the main worktree. `doctor` compares every project range with every other across the whole inventory.

`aligndev project ports` prints the claimed ranges sorted by first port, with paths relative to the root. `aligndev project free-ports --size <n> --within <first>..<last>` returns the lowest block of that size inside the caller's bounds that overlaps no project range of the scan. The bounds come from the deployment's or the team's instructions; the settings hold no machine range. The size is the project's port range: port names × expected concurrent workspaces. Unreadable projects never fail either command: the text form warns on stderr, and the JSON form lists their relative paths under `unknown`. This lookup does not reserve ports. The preparation that `alignfirst setup guide assistant-project` describes writes the block in the selected configuration's `devServer.ports`. AlignDev requires the merged report contract: top-level `workspace` metadata with registry/runtime addresses, `selectionOrigins`, `locations.alignfirst`, `locations.assistantInstructionsFile` and `locations.workspaceRuntime`. It reads nested `config.conventions`, accepts full authored recipes and inventories `workspace.portRange` without evaluating scripts. Missing contract fields, or a `null` `locations.assistantInstructionsFile`, produce an actionable AlignFirst upgrade diagnostic.
